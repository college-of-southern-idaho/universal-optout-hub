Opt-in propagation reviews

The person's opt-in is already honored where it happened. Each review asks one question: does the consent evidence justify opting them back in anywhere else? Approving is an attestation, not a button — explicit opt-outs are never overridden, even if selected.

Service-discovered topology

Departments/pools/codes are discovered from each sending service and used as reporting/attribution metadata only — never a consent-scope authority (ADR-0002). Where a service can't report groupings, codes are ungrouped and can be annotated manually; discovered facts and manual annotations are kept provenance-separate.

Consent-check audit retention

The consent-check API logs every decision to a separate high-volume table (ADR-0004 §7). Pruning enforces the split-retention policy: suppress decisions (opt-out evidence) are kept long-term; allow and error rows age out quickly. Production runs this on a schedule; you can also run it now.

Operational audit-log retention

The operational audit_log records routine activity (ingest, reconcile runs, alerts) and grows unbounded. Pruning removes rows older than the configured window (Retain operational audit log in Settings), while compliance-relevant actions — approval decisions, config changes, API-key create/revoke — are kept indefinitely. Production runs this on a schedule; you can also run it now.

Opt-out sync-lag

Time from each opt-out to confirmed suppression on every target system. The regulatory ceiling is 10 business days (breach); the operational target is minutes (warn = over target).

Sending services

The platforms the hub reconciles. Adding one is two steps: register & connect (pick a type, name it, store credentials, test), then discover & review (pull its pools and codes, confirm, and annotate any the service can't report). Capabilities and credentials govern how the hub talks to a service — never what consent it records (ADR-0002).

Register a service

Pull the service's current pools and codes. Discovered groupings are reporting metadata only. Where the service can't report one, annotate the code by hand — discovered facts and manual annotations stay provenance-separate, and any conflict shows both.

Consent-check API keys

Keys let this service's own sender call POST /api/v1/consent/check before sending (ADR-0004). Each key is scoped to this system, shown once, and revocable instantly.

Settings

Runtime configuration. Changes apply immediately (interval changes reload the scheduler) and are audited. Stored in the database — an env var only seeds the initial default. Secrets (encryption key, database, SSO) are not configurable here.

Consent categories & opt-out cascade

Each service carries a message category (set on the Services screen). An opt-out cascades from its source category (row) to the checked target categories (columns). A protected category — e.g. emergency — is never suppressed; its column is locked. Changes apply immediately and are audited.
